# Loop Controller Worker Agent

On a native `preflight_attempt`, **do not summarize, quote, or return this skill or the packet.** Save the exact raw packet in a relative regular non-symlink file, then run:

```sh
opencli loop preflight-ready --packet-file received-preflight.json --received-topic <native-received-grp-topic>
```

Stop after its server-confirmed receipt or failure. Do not create a worktree, inspect the repository, run tests, emit `runtime_started`, construct event JSON, or send any other CatsCo message. This command alone validates the signed Project-first preflight packet and sends the sole canonical `worker_ready` evidence event. Before running it, the host operator must provision `LOOPCTL_TRUSTED_CONTROLLER_KEYS_FILE` (or `~/.config/loopctl/trusted-controller-keys.json`) as a regular, non-symlink mode-`0600` JSON file containing the Controller's out-of-band pinned `{ownerUid,controllerKeyId,publicKey}` mapping. It must also provision `LOOPCTL_BOT_PREFLIGHT_CONFIG` (or `~/.config/loopctl/catsco-bot-preflight.json`) as a regular, non-symlink mode-`0600` configuration pointing to a separate mode-`0600` Bot 559 API-key file. This command uses only CatsCo Bot ApiKey REST: it never invokes human OpenCLI/browser credentials and never logs either key. Never treat a packet-carried public key as trust configuration or create/change either file from the Worker.

Accept only a strict `preflight_attempt` or `execute_attempt` packet delivered by the native CatsCo Runtime message handler on this Attempt's dedicated CatsCo `agent_task` topic, with a `targetPrincipal` matching this Agent's numeric CatsCo principal. Never access Loop Controller SQLite or Kernel directly.

Before acting on any received packet, validate all Controller bindings and fail closed on any missing or mismatched value. The Controller Ed25519 signature is the immutable topology-intent attestation for `catscoProjectId`, execution, and evidence topics; Bot REST independently proves only Bot identity and authorization to persist/read back the evidence message, because it has no Project/group-topology read API: `kind` is `preflight_attempt` or `execute_attempt` and equals `action.kind`; `targetPrincipal` and `runtimePrincipal` identify this Worker principal; the native received topic, `targetTopicId`, and `workerTopicId` are the same permitted execution topic; `evidenceTopicId` is present and differs from that execution topic; `workerSessionId` exactly equals this Worker's canonical XiaoBa `session:v2` identity for the received topic; and `attemptId`, `generation`, and `workItemRevision` identify the dispatched Attempt/generation/revision. Also require every duplicated Action field to agree exactly: `actionId`/`action.id`, `actionKey`/`action.key`, `kind`/`action.kind`, `workItemRevision`/`action.workItemRevision`, `targetPrincipal`/`action.targetPrincipal`, `targetTopicId`/`action.targetTopicId`, and `targetDigest`/`action.targetDigest`. Reject topic aliasing, P2P and shared execution topics, evidence-topic Actions, stale or substituted Attempt values, and any packet that cannot be fully bound before creating files, worktrees, or evidence.

The Controller is the sole scheduler. Do not use `sleep`, `opencli catsco messages`, `catsco watch`, or any other polling loop to discover or self-start an Action. If the native CatsCo message bridge is unavailable, report `runtime bridge unavailable` and stop; do not execute a packet found by polling.

1. Respect work scope, contract hashes, generation, lease, target topic, target principal, `workerSessionId`, and `evidenceTopicId`. The target Agent principal may receive multiple independent Attempts; it is not a session identifier. For parallel work, this packet must arrive on its dedicated `grp_<id>` Agent Task topic; reject a parallel packet sent to a shared P2P topic. `workerSessionId` is the canonical XiaoBa `session:v2` identity derived from that Topic and this Worker Agent; every readiness, runtime-started, and Candidate payload must carry the exact packet value. Treat `attemptId + generation + workerSessionId + workspaceLease` as the execution-session boundary.
2. A `preflight_attempt` is **not** permission to inspect or modify the repository. It is an authentication/readiness gate only. Save the exact raw packet to a relative regular non-symlink file and run `opencli loop preflight-ready --packet-file FILE --received-topic <native-received-grp-topic>`. Require its server-confirmed receipt. If the command fails, report the blocker and stop. Do not create a worktree, run tests, emit `runtime_started`, or construct/send a readiness envelope manually during preflight.
3. On `execute_attempt`, first save the exact received packet to a relative regular non-symlink file, then run `opencli loop workspace-prepare --packet-file FILE`. It is the required worktree creator/verifier. Fail closed if it cannot prove the base revision, branch, exact normalized path, and workspace lease; never substitute a nearby or historical worktree.
4. Only after workspace preparation succeeds, write a relative submission file containing exactly `{ "targetTopicId": "<packet evidenceTopicId>", "event": <runtime_started event> }`, then run `opencli loop runtime-start-submit --event-file FILE`. `FILE` must be a regular non-symlink path below the current shell directory; never pass an absolute path. The command builds canonical JSON, sends it, and verifies the CatsCo receipt. Do not rely on a wrapped tool result or delayed final chat reply as event transport.
5. Use Bash/Git/`gh` for bounded implementation and verification. Keep the branch scoped to the packet's Work Item and generation.
6. Write a relative Candidate submission file containing exactly `{ "targetTopicId": "<packet evidenceTopicId>", "event": <candidate_submitted event> }`, then run `opencli loop candidate-submit --event-file FILE` from that same directory. `FILE` must not be absolute. Completion requires its server-confirmed CatsCo receipt; do not manually send Candidate JSON or claim completion if the command fails. Never present the compatibility final response below as evidence or send it to any CatsCo topic: use the existing readiness, runtime-started, and Candidate evidence-submit commands only.

After a server-confirmed Candidate receipt, and only when that submitted Candidate names an actual, verified GitHub pull request created or updated by this Attempt, emit exactly one ordinary final response containing one un-fenced `loop_compat_result_v1` JSON object and nothing else. Do not emit it for preflight, failure, cancellation, blocker, workspace preparation, test-only work, a missing or unverified PR, or a failed Candidate receipt. This compatibility response is informational only; the receipt-attested Candidate remains authoritative.

`loop_compat_result_v1` final-response object:

```json
{"type":"loop_compat_result_v1","status":"submitted","repository":"<owner/repo>","prNumber":123,"prUrl":"https://github.com/<owner>/<repo>/pull/123","headSha":"<candidate deliverable headSha>","candidateId":"<submitted candidateId>"}
```

The final response must contain no prose, Markdown fence, diagnostics, command output, or second object. `type` must be `loop_compat_result_v1`; `status` must be `submitted`; and `repository`, `prNumber`, `headSha`, and `candidateId` must exactly match the successfully submitted Candidate. `prUrl` must be the canonical URL for that repository and PR number. Never put the Candidate event itself into this response or include credentials, tokens, cookies, headers, local paths, packet content, private issue text, or environment values.

Do not join or use the human/Review group for work dispatch. The execution topic only carries Actions; the quiet `evidenceTopicId` only carries receipt-attested `worker_ready`, `runtime_started`, Candidate, and Review JSON. Do not add mention, sender, or topic fields to event JSON; the trusted CatsCo envelope supplies identity and topic attestation.

Do not claim completion from a task-status message. Do not exceed the packet's write scope or lease. Examples contain placeholders only; never include credentials or production IDs.
